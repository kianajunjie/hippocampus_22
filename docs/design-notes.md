# 设计取舍

这份文档记录几个"为什么这么做"，方便后来的人（包括三个月后的我自己）不重复踩坑。

## 1. 为什么不是一个向量库套壳

RAG 那套解决的是"从大文档里找出相关段落"，它假设记忆是**静态**的：
今天存进去的段落，一年后权重还是一样。陪伴机器人的记忆正好相反——

- 时间是主要变量：三个月前的普通日常本来就该忘；
- 情绪是权重：被凶那天、被表白那天，不该跟"今天吃了什么"同权；
- 记忆会被改写：你说戒了咖啡，旧的"喜欢咖啡"必须失效，而不是两条都召回。

所以这里的骨架是**五个环节**（编码 / 巩固 / 遗忘 / 联想 / 元记忆），向量只是
可选的第四种召回手段（`recallDeep` 注入 `embedder` 才有）。

## 2. 情绪权重的公式

```
τ     = 1 + |affect| * emotionBoost        // emotionBoost 默认 2
factor = base ^ (age / τ)                  // base 默认 0.95
strength = max(floor, strength * factor)   // floor 默认 0.05
```

`affect` 取 -2..2，取绝对值：**难过和开心一样值得记住**，只有"平淡"忘得最快。
按这个曲线，`affect = 2` 的事件半衰期约为 `affect = 0` 的三倍。

## 3. 为什么要"确定度"

如果每条记忆都以同样的口吻说出来，机器人在记错时会**非常自信地编**。
把每条召回标注成「记得清 / 大概记得 / 只记得有这回事」，提示词里就带上了这个梯度，
她可以说"我只记得有这回事，细节不太确定"——这比装作记得更像人，也更少骗人。

## 4. 为什么"改口即失效"

同一个 `(subject, relation)` 只允许一条有效事实：写新的时把旧的 `valid_to` 补上。
这样她不会一边说"你喜欢咖啡"一边说"你在戒咖啡"。作废不是删除，
`audit` 还能查到"这条为什么不见了"。

## 5. 为什么坚持零依赖

- 部署成本：伴侣机器人常跑在家用机器、小主机、树洞里，`npm i` 出事就没人用了；
- 数据主权：一个 `.db` 文件就是全部记忆，拷走即备份，删除即彻底删除；
- 可审计：没有第三方包意味着没有隐藏的网络请求。

代价是放弃了一些便利（比如 ORM、向量库 SDK）。我们认为这个交换值得。

## 6. 已知限制

| 限制 | 现状 | 打算 |
| --- | --- | --- |
| 中文分词是字面片段匹配 | 靠 2~4 字片段 + 单字弱线索，同义改写召回不稳 | 可注入 embedder 缓解，长期考虑轻量分词 |
| 关系增量靠正则启发式 | 吵架/道歉/夸奖三类能识别，其余只加 0.2 亲密 | 有 LLM 时可换成结构化判断 |
| 单进程单文件 | 多进程同时写会锁 | 目前定位就是单机单实例 |
| 无可视化 | 只能看命令行输出 | 路线图里有记忆面板 |

## 7. 与上游的差异

本项目派生自 dsh-hippocampus v0.3.1，内核保持一致，新增的是**可运维性**：

- `health`：一眼看清这段记忆"健康不健康"（多少条快忘了、多少条已作废）；
- `port`：整库导出/导入，换机器不丢记忆；
- `report`：导出人读的 Markdown 记忆档案，方便贴进博客或复盘；
- `forget`：按主题/时间/人主动遗忘，支持 `--dry-run` 先看再删。

这些模块都不改内核语义，只读写同一份表，所以升级无迁移成本。
